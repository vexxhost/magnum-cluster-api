Kubelet serving certificate verification

By default, every kubelet serves its API (used for kubectl logs, exec, port-forward and metrics) with a self-signed certificate, and the Kubernetes API server connects to it without verifying it. Clusters created with the kubelet_serving_cert_verification_enabled=true label close that gap: every kubelet gets a serving certificate signed by the cluster CA, and the API server rejects any kubelet whose certificate it can't verify. The legacy Heat driver always worked this way.

Requirements

Kubernetes never approves kubelet serving certificates on its own. The driver relies on cluster-api-csr-approver, which runs next to Cluster API in the management cluster. It approves a request only when every name and IP address in it belongs to the OpenStack server behind that node, so floating IPs and additional networks work, and a node can't get a certificate for another node's address. Nothing extra runs inside the workload cluster.

Atmosphere installs and enables the approver by default, so there's nothing to do there. For other deployments, install it as described in its README before users turn the label on.

What the driver does

When the label is set, every node gets a kubeadm patch that sets serverTLSBootstrap: true before the kubelet starts, and kube-apiserver runs with --kubelet-certificate-authority=/etc/kubernetes/pki/ca.crt.

The approver's default cluster selector handles every cluster. If you configure a narrower one, make sure it still matches the Magnum clusters that use this label.

Once the API server verifies kubelets, a new control plane node only becomes ready after its serving certificate is approved, so a cluster with the label won't finish creating or upgrading unless the approver is running.

Troubleshooting

A kubelet whose certificate hasn't been approved can't serve its API. kubectl logs and kubectl exec fail with remote error: tls: internal error, and a new control plane node never becomes ready.

To see the pending requests, run this in the workload cluster:

$ kubectl get csr --field-selector spec.signerName=kubernetes.io/kubelet-serving

The approver records why it didn't approve a request as an event on the matching Machine in the magnum-system namespace. Its observability section lists the events, logs and metrics.

Limitations

  • The label can only be set when a cluster is created.
  • Keep the approver running for as long as any cluster uses the label. Kubelets renew their serving certificates before they expire, and renewals need approval too.
